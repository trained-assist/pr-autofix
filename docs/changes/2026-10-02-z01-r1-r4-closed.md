## Что важно для следующих итераций

1. **Граница поставки — инвариант репозитория, а не привычка одного workflow.** Проверяется сканом
   по всем workflow/шаблонам и исполнением shipped run-step в пустом consumer runner. Оба
   подключены в `staging-gate` — проверка, которую не запускает ни один джоб, не существует.
2. **У каждого записанного факта есть владелец**: читатель (`receipt-check`), исполнитель
   (`retention-sweep`) или явное удаление слота. Класс-гейт в CI:
   `contract-slot-scan --gate-keys retention,tool_commit,gate,patch` — каждый ключ либо имеет
   production-читателя, либо слота больше нет (комментарий, упоминающий удалённый слот, — не
   писатель). Полный `--strict` не включён: 17 legacy-слотов — отдельный issue, общий чек-лист
   молча не смягчается.
3. **Заменяемые устаревшие проверки заменены в том же PR с причиной** (дизайн §2.7):
   `repro-r6:144` (`tool.commit === fixSha`) → три сущности; `repro-r6:160` (`ttl_days > 0`) →
   вычислимый дедлайн (`written_at`), исполнение — отдельной пробой; `repro-r4-cleanup:120`
   («имя скрипта есть  YAML») → shipped run-step.
4. **Манифест поставки пересобран** (25 entries): новый production-модуль обязан быть в
   `payload.manifest.json`, иначе `payload-manifest --check` в CI красный.
