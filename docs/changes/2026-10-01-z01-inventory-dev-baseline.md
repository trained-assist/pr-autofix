# 2026-10-01 — Z01: inventory и общий development baseline

Выжимка решений и граблей карточки. Не история правок, а то, что меняет решения будущей работы.

## Что построено

CLI `scripts/devbaseline.mjs` + библиотека `scripts/lib/devbaseline/*`: `validate`, `verify`,
`context`, `inventory`, `check-docs`, `check-workflows`, `run-derived-check`. Схемы профиля и
адаптера (`contracts/`), пять профилей (`profiles/`), fixture с намеренными дефектами
(`fixtures/onboarding-repo/`), песочница `scripts/sandbox/z01-devbaseline.mjs`, два callable
workflow (`devbaseline-callable.yml`, `ci-fix-cleanup.yml`).

## Решения, которые нельзя переоткрыть молча

- **Нечитаемый репозиторий — это строка данных, а не поломка прогона.** `inventory` по умолчанию
  отдаёт код `0` и помечает строку `unreadable` с причиной; `--strict` превращает нечитаемые строки
  в код `4` для гейта, которому слепое пятно принимать нельзя. Логика: одна недоступная копия из
  25 репозиториев не должна ронять отчёт, который всё равно полезен.
- **Профиль выводится деривацией; `.devbaseline.json` необязателен.** Файл-адаптер закрепляет
  только недеривируемое (check/staging-команда, ref, имена credentials). Иначе онбординг
  превращается в ручную правку в каждом репозитории — ровно то, что baseline отменяет.
- **Значения credentials — нарушение схемы, а не предупреждение.** В таблице живут только имена и
  refs; `assertNoSecretValues` отказывается писать файл, если найдено значение.
- **Construction tasks по умолчанию dry-run.** Генератор отдаёт `construction-tasks.md` и
  machine-readable список; создание Issue — только с `--apply` и после ревью списка.
- **Разделение репозиториев (D6).** `pr-autofix` = движок, схема профилей (единственный источник),
  reusable-workflow, self-test. `software-engineering-playbooks` = регистрация, установщик, мутации
  чужих репозиториев. Playbooks проверяет свои адаптеры против схемы отсюда.
- **Версия = ref вызывающего workflow** (`job.workflow_sha`). Новый log-контракт и настоящий
  callable cleanup не доезжают до потребителей без тега; установщик обязан отвергать ref, где
  cleanup не callable.
- **Log-контракт расширяется аддитивно.** `checkFixDiff().reasons` остался строковым (его читают
  комментарий, статистика и self-test), новое пришло отдельным полем `violations[{rule_id, path,
  message}]`, `compressDiff` получил четвёртый аргумент `meta`.
- **`rule_id` (нарушенное правило) ≠ `reason_code` (почему движок остановился).** Одним полем
  нельзя сказать «что сломано в репозитории» и «почему ничего не починено»: раньше второе затирало
  первое, и красный репозиторий выглядел в логе как «просто нет фиксера». Молчащий check правило
  не выдумывает — остаётся честное `check_command_failed`.

## Грабли (стоили двух раундов правок)

1. **Две реализации одного и того же.** `scanRemote` и `scanLocal` разошлись: живой скан заполнял
   5 колонок из 18, локальный — все 18. Наличие staging определялось по ИМЕНИ файла workflow, из-за
   чего pr-autofix показывал `staging_present=no` при зелёном джобе `staging-gate`. Лечится
   единственным источником (`source.mjs` → `scanSource`) и сверкой «одни фикстуры, два способа
   чтения, строки равны» в песочнице.
2. **Текст сценария разошёлся с кодом.** Сценарий требовал «нечитаемый репозиторий → код ≠ 0», код
   отдавал `0`. Код оказался прав (см. первое решение) — править надо было текст. Дефект заметен
   только прогоном сценария против живой версии: локальные тесты шли по фикстурам и были зелёными
   при неверном обещании в документе.
3. **Negative control на «сломанном» входе проходил на чистом коде.** Чтобы проверка «ломает битый
   вход» имела смысл, нужно убедиться, что она ломает его и только его: иначе она зелёная всегда.
4. **Ловушка проверки exit-кода:** `cmd | sed; echo $?` печатает код последней команды в пайпе, а не
   `node`. Код ловится через `PIPESTATUS` или без пайпа. `node -c` на двадцати файлах «зелёный» сам
   по себе ничего не доказывает — сначала негативный контроль.
5. **`node -c` не ловит битый файл, если его не на чём запустить.** Проверка на временных файлах в
   `/tmp` молча проходит там, где каталога сессии нет; временные файлы — в своей папке.
6. **В песочнице нет npm на PATH — это не баг, а условие.** `run-derived-check` обязан выводить
   команду из `package.json` и запускать её как есть, когда скрипт буквально `node <file>`; иначе
   деривация check-команды становится невидимой для проверки.

## Чего Z01 не сделал (осознанно)

Установка workflow в чужие репозитории и процедура `setup` (владелец — playbooks); коммит
coverage-таблицы и джоб `coverage-drift` (владелец — архитектура); применение construction tasks;
компрессия контекста (Z03). Ни один из этих пунктов не закрывается «частично сделанным
инструментом» — каждый требует своего владельца и своей приёмки.
