## 1. Ценность

**Актор — архитектор-владелец платформы.** Получает одну таблицу и одну процедуру, по которой
агент одинаково быстро входит в любой из ~15 участвующих репозиториев: у каждого известны
check / fix / verify, context-build и log contract, а отсутствующие методы видны как
construction tasks, а не как молчание.

Одна фраза ценности: **владелец перестаёт разбирать каждый новый репозиторий заново, и merge
больше не упирается в «в этом репозитории нет CI/staging».**

**Доказанность: V2** — экспертная оценка архитектора, усиленная наблюдаемым фактом, а не
цифрой пользователей: на момент карточки `ai-agent-runner` не имеет ни одного workflow
(проверено: `GET /repos/trained-assist/ai-agent-runner/actions/workflows` → 0), в
control-plane / integration-gate / error-watcher есть только `repo-context.yml`, обязательного
`staging-gate` нет нигде. Внешнего потребителя у baseline нет — ценность внутренняя, поэтому
V4/V5 не заявляются. Что подняло бы до V3/V4: транскрипт одной реальной onboarding-сессии нового
репозитория по процедуре из шага S5, проведённой не на fixture.

### Кто что получает

| Актор | Выигрыш | Негативная сторона, которую закрываем |
|---|---|---|
| Архитектор-владелец | одна coverage-таблица вместо 15 разных «как тут проверяется» | нет дыр, где merge идёт без зелёного staging |
| Агент-исполнитель | одинаковый быстрый вход: map → bundle → check → fix | не угадывает check-команду и не строит приложение в docs-only репозитории |
| Ревьюер | ссылки на source commit и версии, а не пересказ | не проверяет «на глаз», чем собран результат |

## 2. Шаги

Актор по умолчанию — агент-исполнитель в изолированном чекауте (`engineering_spawn_workspace`),
команда-владелец запускает inventory и читает отчёт. Каждый шаг указывает конкретный блок.

### S1 — Инвентаризация participating-репозиториев
**Блок:** `node scripts/devbaseline.mjs inventory` (новый CLI в pr-autofix) + выходной артефакт
`repo-coverage.json`/`repo-coverage.md` в `trained-agent-architecture` → `docs/inventory/`.

- **КОГДА** запускается `inventory` по списку participating-репозиториев, **ТОГДА** система
  печатает по одной строке на репозиторий: владелец · тип (`docs` / `node` / `python` /
  `mixed`) · profile · check · fix · verify · context · logs · CI · staging, и **ТОГДА** таблица
  коммитится в репозиторий архитектуры.
- **КОГДА** репозиторий не читается (нет прав, репозиторий не найден, битый идентификатор),
  **ТОГДА** строка получает `unreadable` + причину, **ТОГДА** значение **не** выдумывается и
  **не** заменяется пустым «ok», **ТОГДА** команда по умолчанию завершается кодом `0`
  (нечитаемый репозиторий — это ДАННЫЕ, а не сломанный прогон), **ТОГДА** с ключом `--strict`
  завершается кодом `4`, если нечитаемых строк хотя бы одна. Строгая форма — для гейта,
  которому нельзя принять слепое пятно; отчёт по умолчанию — для человека, который читает
  таблицу и сам решает, что с «нечитаемым» делать.
- **КОГДА** идентификатор репозитория в списке не имеет вида `owner/name`, **ТОГДА** строка
  получает `input_invalid` с указанием формы и **ТОГДА** инструмент **не** обращается к API по
  имени, которое он придумал из лишнего сегмента.
- **КОГДА** завершена инвентаризация, **ТОГДА** в таблице и в машинном варианте есть **только
  имена и refs** учётных данных (имя секрета, `repo variable`, ref на binding) и **ТОГДА**
  автопроверка «в inventory нет значений credentials» (AC-40) проходит.
- **Доказательство:** `repo-coverage.md` + `repo-coverage.json`, вывод команды,
  тест отсутствия секретов.
- **Почему код `0` по умолчанию, а не «ошибка»:** нечитаемая строка видна в самой таблице, и
  превращать её в ненулевой код значит заставлять гейт отказывать из-за одной строки из 25.
  Ненулевой код — отдельный режим (`--strict`) для гейта, которому слепое пятно принимать нельзя.

### S2 — Профиль docs-only не получает application build
**Блок:** профили `profiles/*.json` в pr-autofix; тонкий config-адаптер репозитория.

- **КОГДА** репозиторий классифицирован как docs-only, **ТОГДА** его check состоит из проверки
  Markdown/схемы/контекста, **ТОГДА** команда `build` **не вызывается**, **ТОГДА** тяжёлая
  инфраструктура в репозиторий **не добавляется**.
- **КОГДА** репозиторий классифицирован как кодовый, **ТОГДА** check = существующая check-команда
  этого репозитория (не придуманная), fix = `autofix` job из
  `.github/workflows/autofix-callable.yml`, verify = повторный check.
- **КОГДА** репозиторий классифицирован, **ТОГДА** профиль выводится деривацией, **ТОГДА** тонкий
  config-адаптер хранится в репозитории только как закрепление недеривируемого (check/staging-команда,
  ref, имена credentials), **ТОГДА** в таблице видно `adapter: derived | file`. Репозиторий без
  адаптера остаётся полноценным: адаптер не обязателен, он не тащит ручную правку в каждый репозиторий.
- **Доказательство:** config-адаптер репозитория + строка профиля в coverage-таблице.

### S3 — Missing methods становятся construction tasks
**Блок:** inventory + создание issue в `trained-assist/trained-agent-architecture`.

- **КОГДА** у репозитория нет обязательного метода (нет `ci`, нет `staging-gate`, нет AutoFix,
  нет context-build), **ТОГДА** ячейка получает `missing` и **ТОГДА** создаётся construction task
  с владельцем и карточкой плана, **ТОГДА** merge первой карточки I01 в этот репозиторий
  заблокирован до появления `ci` + `staging-gate` (AC-20).
- **Доказательство:** список construction tasks + `missing`-строки в таблице; для
  `ai-agent-runner` — задача на `ci`, для трёх новых репозиториев — задачи на `staging-gate`.

### S4 — Агент входит в репозиторий по профилю
**Блок:** context-build (`node scripts/devbaseline.mjs context`).

- **КОГДА** агент запрашивает контекст репозитория, **ТОГДА** система отдаёт compact map
  (entrypoints / контракты / зависимости / check-команды) + task-relevant bundle + refs на
  полные источники, **ТОГДА** manifest содержит source commit и размер, **ТОГДА** исходный код
  не удаляется.
- **КОГДА** source изменился после последней сборки, **ТОГДА** bundle помечается `stale` и **ТОГДА**
  старый bundle **не выдаётся** как свежий.
- **КОГДА** в репозитории нет контекста (никогда не собирался), **ТОГДА** состояние `missing`, а
  не пустой «успешный» bundle.
- **Доказательство:** manifest/bundle на fixture + stale/missing кейсы.

### S5 — Onboarding нового репозитория — одна процедура
**Блок:** процедура владельца установки — `software-engineering-playbooks` (`src/pr-autofix/installer.js`),
CLI проверки — этот репозиторий (`node scripts/devbaseline.mjs validate|verify|check-workflows`).
**Без** временного ssh-алиаса `vm`.

- **КОГДА** репозиторий добавляется впервые, **ТОГДА** установщик создаёт/включает `ci` +
  `staging-gate` + (для кодовых) AutoFix через reusable-конфигурацию этого репозитория,
  **ТОГДА** в репозиторий попадает только тонкий config-адаптер, **ТОГДА** выполняется
  `run` → собирается `evidence` → выполняется `teardown`, **ТОГДА** повторяемость проверяется
  повторным прогоном с нуля.
- **КОГДА** процедура выполняется повторно на неизменившемся репозитории, **ТОГДА** результат
  no-change (0 файлов, те же SHA) и **ТОГДА** это зафиксировано как evidence.
- **КОГДА** в песочнице нужен доступ к чужой машине, **ТОГДА** процедура использует
  документированный endpoint песочницы, **ТОГДА** зависимости от локального ssh-алиаса `vm`
  нет (алиас может быть снят — процедура продолжает работать).
- **Целевой уровень песочницы — S3 (fixture/локально)**, по прецеденту AC-26: песочница Z01 это
  изолированный чекаут + fixture-репозиторий, облачного сервиса и реальных provisioning'ов нет.
  Live-часть доказательства ограничена read-only чтением GitHub API при генерации таблицы и PR
  установки baseline; локальный PASS нигде не называется облачной проверкой (fidelity declaration,
  AC-06).
- **Граница владельцев (D6):** сценарий и профильная схема живут здесь, мутации чужих
  репозиториев (установка workflow, `setup`) — в `software-engineering-playbooks`. Проверка
  адаптера против этой схемы — здесь; запись в чужой репозиторий — там.
- **Доказательство:** транскрипт setup→run→evidence→teardown на fixture-репозитории.

### S6 — Controlled failure на fixture
**Блок:** `fixtures/onboarding-repo/` (репозиторий с намеренно внесёнными lint/schema-ошибкой).

- **КОГДА** на fixture запускается `run`, **ТОГДА** система даёт **controlled failure**: правило
  срабатывает, rule ID и вывод check видны, ошибка читаема как error event с source/profile/
  request correlation, **ТОГДА** это ожидаемый результат теста, а не падение пайплайна.
- **КОГДА** на fixture запускается **повтор без изменений** (no-change repeat), **ТОГДА** система
  не создаёт patch и **ТОГДА** повтор зафиксирован в логах.
- **КОГДА** ошибка не поддерживается профилем, **ТОГДА** запуск останавливается по cap и **ТОГДА**
  это видно как `needs-human`, а не как «починено».
- **Доказательство:** логи прогона + отсутствие/наличие patch ref.

### S7 — Логи baseline (AC-44, обязательно для приёмки карточки)
**Блок:** log contract профиля.

- **КОГДА** прогон завершается (успех, controlled failure, no-change или отказ по cap), **ТОГДА**
  запись содержит: `rule_id` · `tool` + версия · `attempt_count` · `patch_refs` ·
  `source_commit` · `included_paths` / `omitted_paths` · `budget`, **ТОГДА** correlation
  `source/profile/request`, **ТОГДА** секретов в записи нет.
- **КОГДА** прогон остановился не потому, что всё хорошо, **ТОГДА** `rule_id` называет ПРАВИЛО,
  которое нарушено в репозитории (`docs_heading_missing`, `docs_link_broken`, …), **ТОГДА**
  нарушения перечислены в `rule_violations[{rule_id, path, message}]`, **ТОГДА** причина
  остановки движка названа отдельно (`reason_code` и `stopped_because`, например
  `unsupported_by_profile`), и **ТОГДА** ни одно из этих имён не выдумано: если check не
  назвал правило, остаётся честное `check_command_failed`, а не придуманный id.
  Разделение обязательно: одним полем нельзя сказать «что сломано в репозитории» и «почему
  движок ничего не починил» — раньше второе затирало первое, и красный репозиторий выглядел в
  логе как «просто нет фиксера».
- **КОГДА** лог усечён по retention, **ТОГДА** это зафиксировано (поле retention/TTL), **ТОГДА**
  не выдаётся за «свежий» прогон.
- **Доказательство:** сами логи (AC-44); песочница проверяет и положительный случай (check назвал
  правило), и негативный контроль (check молчит → правило не выдумывается).

### S8 — Новое покрытие не разъезжается со старым
**Блок:** `ci` job в каждом репозитории (проверка baseline при изменении конфигурации).

- **КОГДА** в репозитории меняется тонкий config-адаптер или профиль, **ТОГДА** `ci` проверяет,
  что config-адаптер валиден и что coverage-таблица не устарела относительно него, **ТОГДА**
  расхождение блокирует merge.
- **Доказательство:** зелёный `ci` на актуальной версии PR.

## 3. Не-цели (что сознательно НЕ делаем в Z01)

- Не чиним конкретные падения CI в конкретных репозиториях — это Z02 (bounded AutoFix).
- Не строим сам context-compression builder — Z03; здесь только контракт профиля.
- Не создаём новые сервисы и новые репозитории.
- Не определяем и не храним значения токенов; прод-токены и профили в песочницу не копируются.
- Не добавляем тяжёлую инфраструктуру в репозитории, которым она не нужна (docs-only).
- Не переносим/не дублируем существующие сценарии playbooks (`skill-tool`,
  `pr-issue-status-design`) — они про другие области.

## 4. Крайние случаи

| Случай | Ожидаемое поведение | Evidence |
|---|---|---|
| Пустые данные: нет ни одного workflow | профиль `minimal`: check = no-op с явной пометкой `missing`, не падение | строка таблицы + код возврата |
| Внешний сервис недоступен (GitHub API) | каждая такая строка помечена `unreadable` + причина (HTTP-код); таблица НЕ выдаётся за полную, потому что слепое пятно видно построчно. Код: `0` по умолчанию, `4` под `--strict` | лог + exit code + число unreadable |
| Повтор на неизменившемся репозитории | no-change: 0 файлов, те же SHA, запись `no-change` | лог повтора |
| Нет прав на репозиторий | строка `unreadable` + причина; значение не выдумывается | строка таблицы |
| Stale / missing context | `stale` / `missing`, старый bundle не выдаётся как свежий | manifest |
| Права/ветка: push в `main` запрещён | процедура работает через PR-адаптер, `main` не пишется напрямую | PR вместо push |
| Ошибка вне профиля | стоп по cap, `needs-human` | лог |

## 5. Риски и пробелы (владельцу не задаются — помечены как риск)

1. **Граница «participating repositories» не зафиксирована числом.** Источник строк таблицы —
   раздел «Scope границ репозиториев» плана + `iter1.md`; репозиторий вне списка в таблицу не
   попадает. Если следующий шаг расширит список — это изменение coverage-таблицы, а не тихая
   правка.
2. **Имена блоков (`scripts/devbaseline.mjs`, `profiles/*.json`, `docs/inventory/`) — контракт,
   а не финальные имена.** Сценарий описывает проверяемое поведение, чтобы переименование не
   сломало песочницу и тесты. Разделение ответственности между `pr-autofix` и
   `software-engineering-playbooks` решено фактами на диске — см. §7, решение D6.
3. **Ценность внутренняя (V2).** Главный риск — построить baseline «для галочки». Лечится
   одним настоящим onboarding-прогоном (шаг S5) на реальном новом репозитории, а не только на
   fixture; этот прогон — часть доказательства приёмки.
4. **Точность inventory зависит от доступа к API.** Без прав таблица неполна; неполнота должна
   быть видна в самой таблице, а не в отчёте на словах. Поэтому `unreadable` — это строка с
   причиной, а не тихий пропуск, и `--strict` существует именно для гейта, который такую
   таблицу принимать не должен.
5. **Колонки coverage-таблицы обязаны одинаково заполняться локальным и живым сканом.** Это
   свойство проверяется песочницей: одни и те же фикстуры читаются обоими способами, и строки
   сравниваются. Пока такая сверка не стоит в наборе проверок, таблица снова может разъехаться с
   реальностью.

## 6. Связанные строки приёмки

- **AC-40 · Z01** — coverage-таблица по всем участвующим репозиториям (S1), onboarding
  воспроизводим (S5), значений credentials в inventory нет (S1).
- **AC-44 · Logs I00** — rule ID, tool/version, attempt count, patch refs, source commit,
  included/omitted paths, budget; no-change повтор и failed check (S6, S7).
- **AC-21 / AC-20** — coverage-таблица фиксирует onboarding AutoFix/staging для
  `ai-agent-runner`, `trained-assist-control-plane`, `trained-assist-integration-gate`,
  `trained-assist-error-watcher`; пробелы CI/staging оформлены construction tasks (S3).
- **Общий гейт AC-01…AC-09** — positive path (S5), controlled failure (S6), scoped logs (S7),
  pinned versions (S1/S7), одна процедура setup→run→evidence→teardown (S5), fidelity declaration
  (что эмулировано, что требует live smoke — заполняется на шаге sandbox), секретов в
  логах/trace/issue/commit/docs нет (S1/S7), у песочницы своё имя endpoint/ключ/хранилище (S5).

## 7. Флаги сложности требований

Шкала: 🟢 аддитивно/локально · 🟡 задевает общий контракт, второй репозиторий или интеграцию ·
⚫ неоднозначность (обязана быть снята до дизайна) · 🔴 модель прав, безопасность, биллинг,
необратимая миграция. Требование существует, только если идёт из задачи или из реального
ограничения другой части системы; «так уже написано» источником не считается.

| # | Требование (источник) | Флаг | Челлендж | Решение |

## 8. Что уже в коде и что осталось за карточкой

**В коде (этот репозиторий).** Схемы профиля и адаптера (`contracts/`), пять профилей
(`profiles/`), деривация профиля, `inventory` с 18 колонками и `unreadable`-строками, `verify`
(check → fix → повтор), `context` (fresh/stale/missing), `check-docs`, `check-workflows`,
`run-derived-check`, log-контракт AC-44, callable `devbaseline-callable.yml` (`ci` | `staging-gate`)
и callable `ci-fix-cleanup.yml`. Собственный `ci.yml` содержит job `staging-gate` — репетиция
боевого пути на fixture, поэтому merge в этом репозитории проверяет не только self-test.
Полный набор проверок = три команды из `ci.yml`, всё офлайн:

```sh
AUTOFIX_SELFTEST=1 node scripts/autofix.mjs                                   # self-test
node scripts/sandbox/z01-devbaseline.mjs                                      # staging rehearsal
node scripts/devbaseline.mjs check-workflows --dir .github/workflows         # workflow contract
```

**Принципы, которые нельзя нарушать без нового решения:**

- **Версия = ref вызывающего workflow** (`job.workflow_sha`). Ни log-контракт, ни callable cleanup
  не доедут до потребителей без тега; установщик обязан падать на ref, где cleanup не callable.
- **Log-контракт расширяется аддитивно:** `checkFixDiff().reasons` остаётся строковым (его читают
  комментарий, статистика и self-test), добавляется `violations[{rule_id, path, message}]`, а
  `compressDiff` получает четвёртый аргумент `meta` для `included/omitted paths` и фактического
  расхода бюджета.
- **`adapter` необязателен:** профиль выводится деривацией, файл-адаптер закрепляет недеривируемое.
  Это удерживает онбординг репозиториев от ручной правки в каждом и следует R5.
- **Словарь rule ID** — фиксированный набор; расширение только с новым тегом.
- **Деривация и валидация адаптера живут в одном месте** (`source.mjs`, `profile.mjs`,
  `adapter.mjs`), а строка таблицы строится единственной функцией. Вторая реализация «почти того
  же» — источник расхождения живого и локального отчёта.

**За карточкой (не сделано Z01, оформлено отдельными задачами):**

| Что | Где живёт | Почему не здесь |
|---|---|---|
| Установка `ci`/`staging-gate`/AutoFix в чужой репозиторий, процедура `setup` | `software-engineering-playbooks` (`src/pr-autofix/`) | D6: здесь движок и схема, там мутации чужих репозиториев |
| Коммит coverage-таблицы + джоб `coverage-drift` | `trained-agent-architecture` | Репозиторий-владелец таблицы; без него таблица не зафиксирована рядом с планом |
| Применение construction tasks (`--apply`) | `trained-agent-architecture` | По умолчанию dry-run: массовое создание задач в чужих репозиториях — с явным `--apply` и ревью списка |
| Компрессия контекста (builder) | `Z03` | Z01 даёт контракт профиля и состояния манифеста, не сам builder |

Дизайн, контракты, план проверки и откат — `epic27/z01-design.md` в папке артефактов плана; решения
