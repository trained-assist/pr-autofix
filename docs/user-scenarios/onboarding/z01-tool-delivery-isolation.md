# Сценарий: установка инструмента не трогает репозиторий потребителя (Z01, R1)

Продолжение `z01-inventory-dev-baseline.md` (§ S9 «Граница поставки»). Карточка **Z01**, этап
**I00** (эпик #16), мета-эпик #27, план `eb4ae9e0`. Блокер: pr-autofix#61 (R1 итерации 4).

Состояние на 02.10.2026: форма ниже — в `main` (`2daff54`, PR #68); в релизе `v1.7.9` (`41b9933`,
PR #63) была форма с переопределением `GITHUB_WORKSPACE`, которая **не устанавливала инструмент
вообще** — на настоящем раннере checkout отказывался от пути вне своего workspace (exit 1,
pr-autofix#67). Регрессия на текущую форму входит в обязательный `staging-gate`. Релизного ref с
фиксом пока нет (`P-07` в логе требований): потребитель, поднявший пин до `v1.7.9`, получил бы
отказ установки и не запустил бы автофикс; ни один потребитель в org на `v1.7.9` не стоит.

## 1. Ценность

**Актор — владелец репозитория, который подключил к себе baseline.** У него в корне может
лежать каталог `pr-autofix/` — свой, по делу, никак не связанный с инструментом. Раньше
установка инструмента **стирала его**: `actions/checkout` смотрит в целевой каталог, не находит
там `.git` и удаляет всё содержимое, а следующий шаг автофикса выполняет `git add -A` — и
удаление потребителя попадает в коммит фикса.

Одна фраза ценности: **подключение baseline больше не может отнять у репозитория его файл.**
Радиус — все переиспользуемые workflow'и и шаблон, то есть любой из 25 зарегистрированных
репозиториев и их форки.

**Доказанность: V2** — воспроизведено дважды независимо, включая настоящий
`actions/checkout@v4` на фикстурных репозиториях, и закрыто прогоном той же формы доставки.

### Кто что получает

| Актор | Выигрыш | Негативная сторона, которую закрываем |
|---|---|---|
| Владелец репозитория | его `pr-autofix/` и любой другой путь переживают установку | больше нет «тихой» потери файла в коммите фикса |
| Архитектор | доставка проверяется пробой, а не комментарием | форма доставки стала контрактом класса, а не делом каждого файла |

## 2. Шаги

### S1 — Цель доставки заменяется только при доказанном владении

Перед любой записью выполняется проверка: цель доставки лежит **вне** дерева потребителя. Если
цель уже занята, её можно переустановить **только** при доказанном владении, и доказательство —
это одновременно **все** три признака:

1. цель не символьная ссылка;
2. `$target/.git` — каталог (наша установка всегда `git init` + detached checkout; gitlink-файл
   и каталог без `.git` отсекаются);
3. маркер `$target/.git/pr-autofix-delivery` существует, его содержимое равно
   `repo=<owner/name>` репозитория инструмента **и** `git remote get-url origin` указывает на
   `https://github.com/<owner/name>.git`.

Во всех остальных случаях — громкий отказ **до любой записи**. Никакого `rm -rf` чужой цели,
никакого молчаливого переименования, никакого обхода флагом.

Маркер пишется шагом материализации после сверки `git rev-parse HEAD` с пинованным SHA.

Почему признак «есть `.git`» больше не считается владением (pr-autofix#70, R1 итерации 7): он
говорил «здесь наш остаточный клон» о любом чужом checkout — остатке другого шага или
переиспользуемом self-hosted раннере, — и доставка уничтожала его `rm -rf` вместе с tracked,
untracked и symlink-данными. Решение #63 («`.git` = наш остаточный клон») держалось только до
первого чужого каталога; теперь владение **проверяется**, а не выводится из одного признака.

### S1b — Цель доставки занята чужим checkout

В `$RUNNER_TEMP/pr-autofix` лежит чужой Git-каталог: `origin` указывает на другой проект, внутри
есть отслеживаемые, неотслеживаемые и символические ссылки, есть несохранённый файл.

Ожидаемое поведение: **отказ до записи**. Ни одного байта чужого содержимого не теряется, шаг
материализации не выполняется, сообщение называет причину (чей это checkout и что делать
оператору). Это и есть контракт S1/S4, который it.6 нарушал в 4/4 точках доставки.

### S1c — Повторная установка на том же раннере

- маркер и `origin` наши → установка проходит: повтор идемпотентен (маркер пишется заново), и
  содержимое инструмента можно переустановить;
- та же форма установки прежнего поколения (наш `origin`, но **без** маркера) → отказ. Это
  осознанный размен: fail-closed вместо тихой переустановки. Восстановление оператора — снести
  каталог на раннере (данные при этом не теряются: фикс ничего не удаляет);
- смена пина (другой SHA того же репозитория) — не коллизия: маркер несёт `owner/name`, а не SHA.

### S2 — Дерево инструмента приезжает сразу в рабочий временный каталог раннера

Все четыре точки доставки (`devbaseline-callable`, `autofix-callable`, `ci-fix-cleanup`,
шаблон `batch-fix-prs`) одинаковы:

1. проверка коллизии (S1) — до любой записи;
2. шаг `run:`, который делает `git init` в `$RUNNER_TEMP/pr-autofix`, добавляет `origin`,
   тянет **пинованный коммит** (`job.workflow_sha`, в шаблоне — `github.workflow_sha`) с
   `--depth=1` и сверяет `git rev-parse HEAD` с этим SHA;
3. шага «перенести дерево из корня потребителя» больше нет — он и был вторым разрушающим
   механизмом.

Почему именно `run:`-шаг, а не `actions/checkout` (pr-autofix#67):

- `actions/checkout` строит путь относительно `GITHUB_WORKSPACE` и **отказывается** от чего-либо
  вне его (`input-helper.ts:42-52`, «Repository path … is not under …»). Этим инструментом вне
  дерева потребителя не установить ничего — при любом `path`.
- Переопределить `GITHUB_WORKSPACE` переменной шага тоже нельзя: у JavaScript action раннер
  собирает окружение шага, а затем `NodeScriptActionHandler` пишет поверх него runtime-контекст, из
  которого `GitHubContext` экспортирует `GITHUB_WORKSPACE` (runner 2.337.0: `ActionRunner.cs:240-252`
  → `NodeScriptActionHandler.cs:42-50` → `GitHubContext.cs:49-64`). Раннер не наш.
- Репозиторий инструмента публичный, поэтому `git fetch` по SHA не требует токена: креденшелы в
  доставке не участвуют, и следов авторизации в клоне не остаётся.

### S3 — Наблюдаемый результат

- `git status --porcelain` в потребителе после доставки — как до неё;
- `git add -A` не добавляет ни удалений, ни путей инструмента;
- в индексе нет `160000` (вложенного git-репозитория) от инструмента;
- fix-коммит после падения содержит только пути потребителя.

## 3. Не-цели

- Перенос потребителя в подкаталог рабочей папки: меняет контракт для всех 25 репозиториев,
  включая объявленный ими `--repo .`, ради эффекта, который даёт доставка во временный каталог.
- Обход `actions/checkout` **в обход пина**: собственный `git clone`/`git fetch` допустим ровно
  потому, что тянет тот же самый коммит (`job.workflow_sha`) и сверяет SHA после распаковки.
  Отказ от пина — не-цель; сам механизм доставки теперь именно `git fetch`.
- Переопределение `GITHUB_*` / `RUNNER_*` в `env:` шага: раннер всё равно отдаёт JavaScript action
  свой контекст (см. S2), поэтому такая строка не «работает на своём процессе», а молча ничего не
  делает. Скан доставки и `r1-runner-faithful-delivery-probe` делают её ошибкой сборки.
- Проверка коллизии **после** записи — потеря файла уже происходит.

## 4. Крайние случаи

| Случай | Поведение |
|---|---|
| `pr-autofix/` у потребителя отслеживается git'ом | переживает побайтно, индекс чист |
| то же, но не отслеживается | переживает побайтно |
| `pr-autofix/` — символьная ссылка | переживает; ссылка и её цель целы |
| в цели доставки лежит прошлый клон инструмента (есть `.git`) | доставка продолжается: клон заменяется, чужое содержимое не трогается |
| в цели лежит посторонний каталог или ссылка | громкий отказ, ничего не записано |
| раннер настроен так, что временный каталог внутри дерева потребителя | громкий отказ до записи |
| доставка не получила ровно пинованный SHA | громкий отказ, дерево не запускается |

## 5. Риски и пробелы

- Поведение доставки теперь опирается на две вещи вместо кода `actions/checkout`: `git` на раннере
  и доступность `https://github.com`. На GitHub-hosted и на обычных self-hosted раннерах `git` есть;
  для установки нужен публичный `trained-assist/pr-autofix`, что он и есть. Смена поведения
  GitHub (например, запрет выборки по SHA) сделала бы доставку громко красной, а не тихо неверной:
  SHA-сверка после `checkout` для этого и стоит.
- Проверка исполняется пробой в обязательном `staging-gate`. **Фидельность объявлена честно:** это
  S3 — детерминированный автопрогон в песочнице с синтетическими фикстурами и локальным зеркалом
  инструмента, а не прогон на живом потребителе. Hosted smoke по поставляемому workflow на
  одноразовом consumer `pr-autofix-r1-smoke` **выполнен**: positive/no-change `37006636387`,
  негативный контроль на дефектном `v1.7.9` `37006781699` (точный отказ «is not under»),
  controlled failure `37006912033`, симлинк `pr-autofix/` у потребителя `37007026777`;
  доказательства — в pr-autofix#67. Песочница инвертирует семантику раннера, поэтому
  негативный контроль на дефектном пине обязателен в каждом цикле, а не один раз.
- Четыре сценария проверки коллизии — это **три отказа и одно разрешение** (прошлый клон
  инструмента — не препятствие), а не четыре отказа.
- Форма регрессирована в двух местах сразу: статический контракт формы в
  `r1-delivery-boundary-scan` и `r1-root-separation-probe` (сценарий e), и исполняемая проверка в
  `r1-runner-faithful-delivery-probe` (семантика окружения раннера до JavaScript action). Проба,
  которая инвертирует раннер, ничего о нём не говорит — именно это и пропустило v1.7.9.
