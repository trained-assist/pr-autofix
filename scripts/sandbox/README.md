# Песочница Z01 — как запустить

Одна команда, детерминированный вывод `ok`/`FAIL`, код возврата 1 при провале:

```sh
node scripts/sandbox/z01-devbaseline.mjs          # прогон
node scripts/sandbox/z01-devbaseline.mjs --keep   # не удалять фикстуры после прогона
```

Уровень автономности — **S3** (автотесты с моками внешних зависимостей, фикстуры, офлайн).
Время цикла — **~5 с** (замерено 01.10.2026: 5.4 / 4.4 / 4.9 с). Почти всё время — реальные
`npm test` в node-фикстурах: деривация обязана запускать ту же команду, что и CI, а не
подменять её прямым `node check.js`. Этот же скрипт станет телом джоба `staging-gate` в `ci.yml`
(дизайн §2.5): репетиция боевого пути на фикстуре.

## Что внутри прогона

| Группа | Что проверяет | Фича нужна? |
|---|---|---|
| **A. здоровье песочницы** | синтаксис всех скриптов, что фикстуры действительно сломанные, endpoint существует, `fakebin` без `gh`/`npm`, нет значений секретов | нет |
| **B. сценарий через CLI** | S1 инвентарь, S2 docs-only без build, S3 construction-tasks dry-run, S4 fresh/stale/missing, S6 controlled failure / no_change / needs_human, S7 log-контракт AC-44 | да (T1–T8) |
| **C. границы покрытия** | S5 (владелец — playbooks, T10) и S8 (владелец — architecture, T11) помечены `deferred`, красными не становятся | — |

Группа A зелёная всегда: она доказывает, что провал группы B — про фичу, а не про песочницу.

## Почему это не «зелёная враньё»

Проверки идут через CLI как через **внешний контракт** (AC-19): подпроцесс
`node scripts/devbaseline.mjs` + код возврата + прочитанный log-файл, а не вызов внутренней функции.
Дискриминирующая способность померена двумя подставными реализациями:

| Реализация | ok | FAIL | Что поймала |
|---|---|---|---|
| фичи нет (сейчас) | 8 | 7 | один корень `cli_missing` |
| заглушка «всегда 0», пустая таблица | 18 | 49 | фальшиво-зелёный прогон |
| «лжец»: идеальные коды и log-запись, но stale отдан как fresh | 33 | 34 | семантика (S4, S1) |

## Как песочница изолирована

* **Сеть выключена.** Дочерние процессы получают `HTTP(S)_PROXY=http://127.0.0.1:9` и
  `DEVBASELINE_OFFLINE=1` — попытка сети падает вместо «случайного» успеха.
* **Нет `gh`/`npm` в PATH.** Для `inventory` PATH подменяется на `fakebin` (только `node` и `git`),
  поэтому «construction-tasks не создаёт Issue» проверяется отсутствием инструмента, а не декларацией.
* **Свой endpoint.** `endpoint.git` — локальный bare-репозиторий (AC-09), а не ssh-алиас `vm`.
* **Своя папка.** Артефакты — в `.devbaseline-sandbox/` (в `.gitignore`), не в общем `/tmp`.
  Переопределяется через `DEVBASELINE_SANDBOX_TMP`.
* **Секретов нет.** Прогон проверяет и фикстуры, и свои же log-записи сканом на значения (AC-07/AC-08).

## Контракт, который песочница закрепляет

Коды возврата и имена флагов — из дизайна §2.1 (`validate` 0/3 · `verify` 0/1/2/3 ·
`context` 0/2/3 · `inventory` 0/4 · `check-docs` 0/1). Два минимальных добавления,
обязательные для офлайн-детерминизма:

* `inventory --repos <file>` — список репозиториев вместо `inventory/repos.json`; записи
  допускают поле `path` (локальный checkout) для офлайн-скана.
* `verify --log <file>` — явный путь log-записи (AC-44) вместо stdout.

**Известное граничение.** S7 проверяет полноту и корректность *формы* log-записи (набор полей
AC-44, `rule_id` из фиксированного словаря, `no_change` → пустой `patch_refs`), но не её
достоверность: идеально сфабрикованная запись форму проходит. Достоверность лога ловится
семантическими проверками S1/S4/S6 (это и показал пробник «лжец»).

## R6 — регрессия receipt'а (красный тест до фикса)

```sh
node scripts/sandbox/repro-r6-receipt.mjs          # exit 1 = дефект воспроизведён
```

Исполняемый путь failed→fix→verify→receipt с **stub-провайдером** (локальный llm-ladder
HTTP-сервер) и **mock GitHub** (`gh`-заглушка на PATH). Проверяет, что `ci-fixer-stats.json`
(AC-44) несёт фактические данные. На неисправленном коде красный: `patch_refs: []`,
`included_paths: []`, `budget.diff_tokens_used: 0`, `tool.commit` = env, а не реальный SHA.
Зелёным становится после wiring'а meta в production call sites (pr-autofix#35).

## R1 · коллизия каталога потребителя (красный тест до фикса, pr-autofix#61)

```sh
node scripts/sandbox/r1-consumer-collision-probe.mjs [--checkout <дерево actions/checkout>]  # exit 1 = дефект воспроизведён
```

Единственная команда воспроизведения блокера итерации 4: **настоящий** (не эмулированный)
`actions/checkout@v4` dist исполняется на синтетическом потребителе, который УЖЕ владеет
каталогом `pr-autofix/` (tracked-файл / untracked-файл / symlink), затем дословно выполняются
поставляемые `run:`-блоки из живых workflow-файлов. Проверки: побайтная сохранность дерева
потребителя, неизменность `git status`, пустота `git add -A` (ровно ожидаемый набор), отсутствие
gitlink `160000` — плюс anti-vacuity: дерево инструмента обязано существовать ВНЕ корня
потребителя, иначе «доставка ничего не сделала» не пройдёт зелёным.

Офлайн и без секретов: инструмент — локальный bare-зеркало репозитория через
`url.<mirror>.insteadOf`, `GIT_ALLOW_PROTOCOL=file` запрещает сеть (зелёный прогон не может быть
заслугой сети), токен синтетический. Источник dist фиксируется: `--checkout` (офлайн) либо
tarball codeload по пину `11d5960a…` (CI), sha256 dist пишется в `results.json`.

На неисправленном коде (58a5ab2) красный во всех 6 сценариях: ` D pr-autofix/consumer-owned.md`
попадает в индекс после `git add -A`, symlink-вариант хуже — checkout пишет дерево инструмента
ВНУТРЬ потребителя через symlink и `git add -A` ставит ~70 файлов инструмента как `A`. Зелёным
станет, когда поставка разведёт корни ДО материализации.

## R1 · доставка под реальным порядком окружения раннера (красный тест до фикса, pr-autofix#67)

```sh
node scripts/sandbox/r1-runner-faithful-delivery-probe.mjs [--checkout <дерево actions/checkout>]  # exit 1 = дефект воспроизведён
```

Проба `r1-consumer-collision-probe` и `r1-root-separation-probe` когда-то давали `env:` шага
приоритет над контекстом — обратно тому, что делает раннер. Из-за этого релиз `v1.7.9`
(`41b9933`), где доставка **вообще ничего не устанавливала**, был объявлен чистым.

Раннер 2.337.0 пишет runtime-контекст ПОВЕРХ окружения шага
(`ActionRunner.cs:240-252` → `NodeScriptActionHandler.cs:42-50` → `GitHubContext.cs:49-64`),
поэтому строка `env: GITHUB_WORKSPACE: …` у JavaScript action не работает. Эта проба строит
окружение в этом порядке, исполняет все четыре поставляемые точки доставки и требует, чтобы
дерево инструмента **реально установилось** в `$RUNNER_TEMP/pr-autofix` ровно на пинованном SHA
(фикстура владеет `pr-autofix/` тремя способами: tracked / untracked / symlink).

Форма закреплена статически в той же пробе: **ноль** шагов с `GITHUB_*`/`RUNNER_*` в `env:`.
Проверки коллизии — 4 сценария: 3 отказа и 1 разрешённое состояние (прошлый клон инструмента).
Вердикт различает **отказ установки** и **потерю содержимого потребителя** — это разные события,
и называть их одним словом было ошибкой R2.

Офлайн: инструмент — локальное bare-зеркало через `url.<mirror>.insteadOf` (обе формы URL),
`GIT_ALLOW_PROTOCOL=file`; `actions/checkout` dist нужен только если доставка всё ещё на нём
(после фикса — не нужен и не скачивается). Красный на `c6291a1` (= v1.7.9): 4/4 точки доставки
переопределяют переменную раннера, отказ установки 6/6, потребитель при этом невредим.
